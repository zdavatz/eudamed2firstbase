# EUDAMED download, rate limits, mirror

- **download.rs**: Shared download module (GUI + CLI). `DownloadProgress` trait abstracts progress reporting. `run_download()` does parallel listing downloads (50 threads default) → `listing_cache` SQLite table → on-the-fly version classification against `udi_versions` (cached prepared stmt, end-of-SRN counters `[N↑ new, N↑ udi, N↑ budi, N same]`) → pre-download version check skips unchanged devices → parallel detail/basic download with retry → version indexing into `udi_versions`. EUDAMED API silently caps `pageSize` to 20. **`filter_unchanged` disk-completeness guard (v1.0.57):** a version-match only counts as "unchanged" (skip) when the cached `detail/<uuid>.json` AND `basic/<uuid>.json` both exist non-empty. If a cache file is missing the device is re-downloaded, its `udi_versions` row is dropped (`version_db::delete_version`), and its stale `firstbase_json/<uuid>.json` is removed so the convert step's output-missing fallback rebuilds it. Without this, a device whose basic file was lost (failed bulk fetch, deleted) stayed permanently skipped → convert got `basic_udi=None` → `globalModelNumber`=GTIN, no `MODEL_NUMBER`/`globalModelDescription`/EAR → GS1 097.116/097.025/097.054 on every push (the FR-MF-000000602 / BR-MF-000014512 mass-rejection, 221 devices). **v1.0.71 — rate-limit-resilient download (all download modes) + GUI status bar:** the listing + detail/basic download in `run_download` shared the flaw Mode 6 had — at 50 threads against EUDAMED's ~60-req/60s rate limit it threw **49×429** and the listing loop **`break`-d on a 429, truncating pagination** (Maik's 82-SRN Mode-0 run extracted only **695 of ~21,813** UUIDs; DE-MF-000018836 got 40 of 4795; 28 SRNs got 0). Reproduced locally (49×429, 695/21813 — not Windows-specific). Fix: a shared `eudamed_get()` helper (status-aware agent, **honors `Retry-After` on 429**, retries with backoff) used by the listing loop (retries the page instead of breaking → no truncation), `parallel_fetch` (detail/basic), and the completeness retry; concurrency lowered 50 → `listing_threads` 6 / `parallel_threads` 12 (basic), with a separate `detail_threads` 50 (detail is far less throttled — it refetched 5372/5372 fine at 50). Validated: the same 82 SRNs now extract **21,813 UUIDs, 0 truncations** (DE-MF-000018836 all 4795 listed). **Known limitation (v1.0.72 follow-up):** the *reactive* retry-on-429 guarantees completeness but is *slow* under heavy throttling — 12 threads each eat a 60 s `Retry-After` wait in lockstep → ~12/min, far below the 60/min budget; a *proactive* shared rate-limiter (pace ~1 req/s to avoid 429s entirely) would restore throughput. New `DownloadEvent::Status { phase, done, total }` → GUI `WorkerMsg::DownloadStatus` → an `egui::ProgressBar` (`Listings 45/82`, `detail 240/648`, `basic …`) in both split layouts so long rate-limited downloads are transparent; CLI ignores `Status` (its Log lines already cover stderr). **v1.0.72 — proactive shared rate-limiter (the throughput fix):** v1.0.71's *reactive* retry-on-429 guaranteed completeness but collapsed to **~12/min** under heavy throttle (N threads each eat a 60 s `Retry-After` wait in lockstep). Measured 2026-06-25: EUDAMED's ~60-req/60 s budget is **SHARED across ALL device endpoints, per-IP** — draining detail's 60-request budget then immediately hitting basic returned **0 successes, instant 429**. New `RateLimiter` (next-slot token bucket; `.max(now)` caps post-gap catch-up to one request, never a burst; `rate_interval_ms` default 1050 ms ≈ 57/min) gates **every** `eudamed_get` across listing + detail + basic via ONE shared instance created in `run_download` — proactively pacing requests *under* the budget so 429s never happen. Proven: 130 mixed detail+basic requests across 2+ rate windows = **0 throttles, steady 57.4/min** (vs ~12/min reactive). Thread counts are now throughput-irrelevant (uniform 6 — a few to overlap network latency / survive a slow request; the limiter caps the aggregate); the `Retry-After` retry stays as a safety net (rarely fires now). **ETA reality:** 21,813 devices ≈ 44,500 shared-budget requests ÷ 57/min ≈ **~13 h from one IP** — the unbeatable single-IP floor; per-IP throttling means splitting SRNs across separate machines is the only legit way to parallelize (no proxy/IP-rotation — that's circumventing a deliberate protection). `rate_interval_ms` is configurable for tuning. (A single big SRN's *listing* is latency-bound on one thread — pages paginate sequentially — so it runs below 57/min; the multi-SRN listing + detail/basic phases use 6 threads and hit the paced rate.) **GTIN mode (v1.0.74):** `DownloadConfig.gtins` (CLI `download --gtin <G…>` / `--gtin-file <file>`) takes precedence over `srns` in the listing step. `download_listings_by_gtin` → `download_listing_for_gtin` resolves each GTIN via the listing endpoint's **`primaryDi=<GTIN>`** filter — the ONLY param that filters (measured: `udiDi`/`udiDiCode`/`code`/`deviceIdentifier`/`keyword`/`search`/… are silently ignored and return all 2.6M devices; `primaryDi` returns the single match). Writes the item to `listing_cache` with its real `manufacturerSrn` (so a GTIN-fetched device can still be repushed by SRN), returns the same `(uuid, version, budi_version)` tuple as SRN listings → the rest of `run_download` (version check, detail/basic fetch via the shared `RateLimiter`, indexing) is identical. A GTIN with no device logs `no device in EUDAMED` and is skipped. Basic UDI-DI URL is `…/api/devices/basicUdiData/udiDiData/{uuid}` (appended to `/devices`, NOT `/udiDiData`). **Convert-path fix (v1.0.74):** `download --convert` now `set_current_dir(app_data_dir())` before `process_eudamed_json_dir`, which resolves input (`eudamed_json/detail`), output (`firstbase_json/`), DB (`db/version_tracking.db`), and Basic-UDI cache (`eudamed_json/basic`) all CWD-relative — previously the convert read a CWD-relative `eudamed_json/` that didn't exist unless you ran from the data dir, so `download --convert` silently produced no output when run from the repo dir.
- **Basic UDI-DI fetch-on-miss in convert (v1.0.57):** gui.rs convert and `reconvert_uuids_from_detail` (Mode 5 / `regenerate`) now fetch the Basic UDI-DI on-demand (`fetch_basic_udi_di`) when it is not in the loaded cache — same safety net the `eudamed_json` CLI mode already had. Prevents the silent `basic_udi=None` fallback (097.116/097.025/097.054) when reconverting without a fresh download. NOTE: the push step pushes **all** pushable files in `firstbase_json/` (not SRN-scoped); rejected files stay there and are re-pushed every run, so a stale bad output keeps failing until it is reconverted correctly or removed.
- **Hardened `fetch_basic_udi_di` (v1.0.65):** the on-miss fetch was single-shot — any transient EUDAMED hiccup (timeout, 429, 5xx, partial body) returned `None` silently. During a 5000-device bulk Mode 5 / Mode 0 reconvert that left `basic_udi=None` for the unlucky devices → empty `GlobalModelInformation` (no `globalModelNumber`, no `globalModelDescription`, and for legacy no `B-<GTIN>` either) → **097.025** on every push, plus 097.054 noise. This was the FR-MF-000000602 / CH-MF-000009933 / BR-MF-000014512 **50-device reject batch** (verified: 48/50 had no basic file in cache; all fetch fine from the API with full deviceName/deviceModel/GMN; reproducing the convert with basic present yields correct output and the rejects vanish — it was *never* an EUDAMED data gap or a mapping logic error). Now: a `ureq::Agent` with a 15 s `timeout_global` + a 4-attempt retry loop with linear backoff, and **parse-before-cache** — the body is only written to `eudamed_json/basic/<uuid>.json` (and returned) when it parses to a Basic UDI-DI carrying a non-empty `basic_udi.code`, so an error page can no longer poison the cache and then count as a "present" basic file forever. `load_basic_udi_cache` already drops unparseable files (`parse_basic_udi_di(...).ok()?`), so a previously-poisoned file → cache miss → hardened re-fetch overwrites it with a valid body. **Fixing requires a force-reconvert: Mode 0's convert hash-skips a device whose detail JSON is unchanged AND whose (stale, empty) output still exists, so it never reaches the fetch-on-miss — run Mode 5 (Reconvert + Repush SRN), which ignores the hash and always reconverts.** Remaining after the basic-fetch fix: the genuine **097.116** question on legacy `B-<GTIN>` (it was previously *masked* by `basic_udi=None`; once basic loads, legacy emits `globalModelNumber=B-<GTIN>` and 097.116 can fire again — the `is_valid_gmn`-gate decision, still open).

## EUDAMED request budget (changes over time)

- **Measured 09.10.2026: ~20 requests per 60 s per IP** (20 OK, then `429` + `Retry-After: 60`), down from the ~60/60 s measured in June 2026 (v1.0.72). Measured passively from the nightly log: ~20 devices in ~20 s, then ~60 s silence, repeating every ~80 s. The numbers "57/min" and "≈ 3.5 h per deep-scan slice" elsewhere in this file describe the June budget.
- **`EUDAMED_RATE_MS`** (`download::default_rate_interval_ms`) overrides the pacing of the shared `RateLimiter` without a rebuild; the built-in default stays `DEFAULT_RATE_INTERVAL_MS` = 1050. `download`, `check` and `deep-scan` read it (`deep-scan --rate-ms` still wins); `mirror` and `sync-actors` have their own `--rate-ms`. The nightly wrapper exports `EUDAMED_RATE_MS=3200` (~19/min, no penalty) — at 1050 ms every round ran into the 60 s penalty (~15/min; the deep-scan slice of 08.10.2026 took 14.5 h). Unit test `download::rate_tests::rate_interval_override`.
- **Listing pages of 300 (09.10.2026):** the SRN listing now pages with **`size=300`**. EUDAMED caps `pageSize` at 20 but honours `size` up to 300 (measured: 46 instead of 680 pages for a 13'583-device SRN, same item shape) — the nightly listing pass drops from ~2'200 to ~250 requests. The older notes "EUDAMED API silently caps `pageSize` to 20" stay true for `pageSize`; `mirror` has always used `size`. Source of the hint: the unofficial API reference github.com/openregulatory/eudamed-api (no bulk download exists).
- **deep-scan fetches the Basic UDI-DI once per record (09.10.2026):** devices sharing a Basic UDI-DI get byte-identical bodies from `/basicUdiData/udiDiData/{uuid}` (300/300 cached pairs identical; in a 6'000-device sample only 2'360 distinct records). The listing exposes the record's ULID as **`basicUdiDiDataUlid`** (`basicUdiDataUuid`, `basicUdiDataVersionNumber` and `lastUpdateDate` are null/0 there) and it equals the top-level `ulid` of the basic body (289/289). It is stored in the additive column **`listing_cache.budi_ulid`**. `group_by_basic_record` groups a slice by that ULID (fallback: `ulid` of the cached basic file; no key → fetched alone as before); per group the basic body is fetched via the first member and reused for the others **only after its own ULID matched the group key** (`basic_record_ulid`) — on a mismatch or a failed fetch every member keeps fetching its own, i.e. the old behaviour. The summary line reports `Basic UDI-DI: N request(s) saved`. Dry-run proof: 40 devices / 6 records → 46 instead of 80 requests. Unit tests `deep_scan_group_tests::*`.
- **One-off GTIN lookups for article lists live in `cosmon`** (github.com/zdavatz/cosmon, `cosmon eudamed <list>`, since 09.10.2026): a Rust port of the `primaryDi` listing lookup that writes a resumable CSV (trade name, manufacturer, SRN, risk class, status, Basic UDI-DI) and touches no eudamed2firstbase data. Use it instead of `download --gtin-file` when only a match against EUDAMED is needed; detail/Basic-UDI download, conversion and the GS1 push stay here.
- **The budget is shared by every EUDAMED job on this IP.** A one-off `download --gtin-file` next to the nightly `check`/`deep-scan` starves both (instant 429 for everyone). Run such jobs only when no nightly process is active, and give them their own data dir (`HOME=<dir>` — the data dir is `$HOME/eudamed2firstbase`) so production data stays untouched.
- **Overlap guard in the nightly wrapper (09.10.2026):** a run can exceed 24 h, so `nightly_eudamed_check.sh` skips a new run while the previous one is active (`flock -n` on `~/eudamed2firstbase/log/nightly_check.lock` plus `pgrep` for a running `check`/`deep-scan`) and logs `===== nightly check SKIPPED … =====`. A skipped night is caught up by the next run.
- No second IP / proxy on the same machine to multiply the budget — that circumvents a deliberate limit. A second machine with its own task is the only legitimate way to parallelize.

- **`sync-actors` subcommand + `actors.rs` (v1.0.85):** `sync-actors [--rate-ms N]` fetches the **full EUDAMED actor / economic-operator registry** (~48'000 actors — manufacturers, ARs, importers) from the public `…/api/eos` listing and upserts each into a new **`actors`** table keyed by SRN, so **every SRN can be resolved to its manufacturer/AR name (+ country, address, email, role, status)** independent of any device. `/api/eos` is the actor analogue of the device `udiDiData` listing (same 20-item server cap → ~2'399 pages; supports an `srn=` filter). Reuses the device-download choke-point verbatim — one shared `RateLimiter` + `eudamed_get` (honors 429 `Retry-After`, paces ~57/min under EUDAMED's ~60/60 s shared budget). **v1.0.87/88 — per-country pagination (the real throughput fix):** the unfiltered `/eos` listing uses **deep-offset pagination** — `page=N` makes EUDAMED scan+discard `N×20` rows, so page latency grows from ~2 s (early) to ~12–15 s (past offset ~20 k; measured: a lone `page=1200` is a clean HTTP 200 that takes **14.5 s**, NOT a 429 — the endpoint itself is slow, so pacing can't help). A single unfiltered walk crawls at ~5 pages/min ≈ **7 h**, and **parallelizing through it does NOT help** — `/eos` tolerates only ~30/min sustained, and any multi-thread burst trips a **429 → 60 s `Retry-After` lockstep** (all threads sleep in sync → ~5/min; verified at 16/12/8/6/2 threads, all collapse). Fix (v1.0.88): **partition by `countryIso2Code`** (the filter works, one per [`mappings::ACTOR_COUNTRY_CODES`] — 251 ISO codes, ~108 non-empty). Each country's list is small (max a few k), so **no page reaches a deep offset** — every page stays ~2 s and throughput becomes rate- not latency-bound. Two phases: (1) probe page 0 of each country (gets `totalElements` + stores it); (2) fan out the remaining `(country,page)` work. **Default `--threads 1`** — a single thread self-limits via latency, *cannot* lockstep (a lone 429 is just absorbed and it continues, never stuck), and on fast per-country pages sustains ~30/min = the `/eos` ceiling anyway, so 1 thread is both safest and fastest; `--threads N`/`--rate-ms N` override at your own 429 risk. DB writes serialize behind a `Mutex<Connection>` (held microseconds; fetch is outside the lock). Full sync ≈ 85 min. **Re-runnable/updateable:** `upsert_actor` is `INSERT … ON CONFLICT(srn) DO UPDATE`, so existing rows refresh in place and new actors are added; no deletes. **Purely additive schema (backwards-compatible):** `open_db` creates `actors` via `CREATE TABLE IF NOT EXISTS` (+ country/role indexes); no *pre-existing* table (`udi_versions`/`listing_cache`/`push_*`/…) is touched, so old binaries simply ignore the new `actors` table. (The only `ALTER` is the v1.0.86 additive column migration on `actors` itself, below.) Devices link via a read-only join `actors.srn = listing_cache.srn` (no FK constraint). `actorStatus` `{code:"refdata.actor-status.active"}` is flattened to its last dotted segment (`active`). **v1.0.86** adds `geographical_address` (EUDAMED's full concatenated address — the structured `streetName`/`buildingNumber` are often null, so this is the reliable address), `country_type` (EU_MEMBER_STATE/…) and `abbreviated_name`; `add_column_if_missing()` (PRAGMA-guarded `ALTER TABLE … ADD COLUMN`) migrates an existing `actors` table additively, and a re-run of `sync-actors` backfills them via upsert. Motivation: `listing_cache.manufacturer_name` covered 2'426/2'429 device-SRNs; `sync-actors` resolves all of them (incl. the 3 with empty per-device names) plus the full registry beyond devices we've downloaded.

## Local EUDAMED Mirror (`src/mirror.rs`)

`mirror` mirrors the **public** EUDAMED corpus into SQLite. Three phases, each resumable
and separately runnable: `--crawl` (listing → `devices_listing`, checkpointed in
`crawl_pages`), `--details` (per-device detail + Basic-UDI → `device_details`, stored as
verbatim JSON), `--flatten` (JSON → `device_details_flat`, ~70 parsed columns). `--all`
or no phase flag runs all three. Options: `--db`, `--gtin-file` (restrict details to a
GTIN list), `--threads` (default 8), `--rate-ms` (default 120).

Things that are easy to get wrong here:

- **Page size caps at 300.** Asking for 500/1000 still returns 300; ~10.8 k pages cover
  the ~3.25 M devices. Do not "optimise" by raising it.
- **Throughput is server-bound at ~60 req/min per IP**, not CPU-bound. A burst returns
  `HTTP 429` with `Retry-After: 60`. Everything goes through `download::eudamed_get`
  (paced by `RateLimiter`); raising `--threads` only buys 60-second penalties. A Python
  prototype hit exactly the same ceiling — rewriting in Rust bought resumability and
  reuse, not speed.
- **Page rows + checkpoint are written in ONE transaction** (`insert_listing_page`).
  Split them and a crash either duplicates 300 devices on resume or loses them silently.
- **`Connection` is `Send` but not `Sync`.** The worker threads share a `Mutex<Connection>`
  that OWNS the connection; a `Mutex<&Connection>` does not compile.
- **`issuingAgency` is always null in the listing payload** (it is only populated in
  detail merges). Identify GS1 GTINs by the DI being all-numeric instead.
- **Actor country/address are FLAT keys** on the actor object (`countryName`,
  `geographicalAddress`), not a nested `address.country.name`. Reading them as nested
  yields empty columns with no error — `actor_country_and_address_are_read_flat` guards this.
- **Store the raw JSON.** The API is undocumented; on a schema change re-run `--flatten`
  rather than re-crawling for ~5 h.

Unit tests cover GTIN normalisation (EAN-13 ↔ GTIN-14), `refdata.*` code stripping,
multilingual text selection, both-payload flattening, a missing Basic-UDI payload, and
the flat-actor-field regression.

## EUDAMED Public API

- Base: `https://ec.europa.eu/tools/eudamed/api/devices/udiDiData`
- Listing: `GET ?page=N&pageSize=300&iso2Code=en&languageIso2Code=en` (capped to 20 server-side, 0-based pagination).
- Listing with SRN: `GET ?...&srn=<SRN>` — Swiss SRNs (`CH-MF-*`/`CH-AR-*`) not in EUDAMED.
- Listing by GTIN: `GET ?...&primaryDi=<GTIN>` → the single device whose UDI-DI primary code matches (exact match; GS1 GTIN-14). This is the ONLY working device-code filter — `udiDi`/`udiDiCode`/`code`/`deviceIdentifier`/`keyword`/`search`/… are silently ignored and return the full ~2.6M-device set. Used by `download --gtin`.
- Detail: `GET /{uuid}?languageIso2Code=en`.
- Basic UDI-DI: `GET /basicUdiData/udiDiData/{uuid}?languageIso2Code=en`.
- Detail lacks manufacturer/AR SRN, risk class, MDR booleans → merged from BUDI cache and/or listing data.
- Serde structs use `#[allow(dead_code)]` (parsing-only fields).
